# Input compatibility in 0.1.0

BREAKING means a formerly accepted input may be rejected. NON_BREAKING indicates a supported widening or metadata change. UNKNOWN means this engine cannot establish compatibility. Changes are independent findings, not a proof of the complete schema's satisfiability. Paths use JSON-pointer escaping. Required changes deliberately use a property-identity location (`/required/locale`, not a positional array index); the last segment names the affected property even if it is not declared in properties. This stable reporting location is not a literal index into the required array. All other paths locate the changed keyword/subschema.

| Rule / kind | Example before → after | Severity and reasoning |
|---|---|---|
| tool_added | missing → `echo` | NON_BREAKING: existing names remain available |
| tool_removed | `echo` → missing | BREAKING: calls lose their target |
| description_changed, title_changed, examples_changed, deprecated_changed | `"old"` → `"new"` | NON_BREAKING: only these four annotations at schema locations, including complex subtrees. Literal enum/const data is never treated as documentation |
| annotations_changed | `readOnlyHint:true` → false | NON_BREAKING in v0.1: advisory behavior hints; callers should review these changes |
| output_schema_changed | `{}` → `{type:"string"}` | UNKNOWN: output compatibility is not inferred |
| required_added | `[]` → `["x"]` | BREAKING: omission can fail |
| required_removed | `["x"]` → `[]` | NON_BREAKING: omission becomes allowed |
| property_added | `{}` → `properties.x:{}` | NON_BREAKING only when old additionalProperties was false and neither side has patternProperties, or the new schema is true/empty/documentation-only with no patterns. Otherwise UNKNOWN: old calls may already send any value under this name. A simultaneous required addition is separately BREAKING |
| property_removed | `properties.x:{}` → absent | No finding if the old schema was false or a provably empty finite domain and the resulting additionalProperties is false with no resulting patterns. For a known inhabited simple/finite old schema and resulting false: BREAKING. Otherwise UNKNOWN, including unproved unsatisfiability |
| type_changed: constraint added/removed | absent → string / string → absent | BREAKING / NON_BREAKING: constrains / expands the accepted domain |
| type_changed: subset/superset | number → integer / integer → number | BREAKING / NON_BREAKING: integers are a subset of numbers |
| type_changed: nullable union | string → `["string","null"]` | NON_BREAKING; reverse BREAKING |
| type_changed: disjoint/overlapping | string → number / `[string,number]` → `[string,boolean]` | BREAKING / UNKNOWN: disjoint domain / neither set contains the other |
| enum_values_removed | `[1,2]` → `[1]`, or absent → `[1]` | BREAKING: accepted values disappear |
| enum_values_added | `[1]` → `[1,2]`, or enum → absent | NON_BREAKING: accepted values expand |
| const | `const:1` → `enum:[1]` | Intersect const with enum when both exist. Equal effective finite sets: no change. Replacement emits removal/addition using enum change kinds; const-origin changes point to /const, enum-origin restrictions to /enum |
| additional_properties | absent/true → false | BREAKING; reverse NON_BREAKING. Absence defaults to true |
| schema-valued additionalProperties | false → `{type:"string"}` | UNKNOWN; identical schemas produce no finding |
| minimum, exclusiveMinimum, minLength, minItems | 1 → 2 | Applicable tightening is BREAKING; loosening NON_BREAKING. Numeric lower bounds are combined before comparison; irrelevant instance types produce no finding |
| maximum, exclusiveMaximum, maxLength, maxItems | 2 → 1 | Applicable tightening is BREAKING; loosening NON_BREAKING. Numeric upper bounds are combined; integer bounds are rounded to the accepted integer endpoints |
| uniqueItems | absent/false → true | BREAKING; reverse NON_BREAKING |
| multipleOf, pattern, format | 2 → 3 / `a` → `b` / email → uri | UNKNOWN for any changed constraint, including addition/removal; no language or divisibility inference |
| items | `{type:"number"}` → `{type:"integer"}` | Recurse at `/items`; narrowing is BREAKING |
| nested properties | `properties.a.properties.b` | Recurse at `/properties/a/properties/b`; escape `~` as `~0`, `/` as `~1` |
| $ref | local target string → number | UNKNOWN. Local pointers are expanded only for identity; unresolved pointers and cycles yield UNKNOWN |
| $defs, definitions | definition changes | Documentation-only differences emit exact annotation paths; otherwise one complex_schema_changed UNKNOWN per changed keyword subtree |
| oneOf, anyOf, allOf, not | alternative changes | Identical schema-aware canonical subtree: no finding; documentation-only differences: exact NON_BREAKING findings; otherwise complex_schema_changed UNKNOWN |
| if, then, else | condition/branch changes | Identical subtree: no finding; documentation-only differences: exact NON_BREAKING findings; otherwise complex_schema_changed UNKNOWN per keyword |
| dependentRequired, dependentSchemas | dependency changes | Identical subtree: no finding; documentation-only differences: exact NON_BREAKING findings; otherwise complex_schema_changed UNKNOWN |
| patternProperties, prerequisites | subtree changes | Identical subtree: no finding; documentation-only differences: exact NON_BREAKING findings; otherwise complex_schema_changed UNKNOWN |
| keyword_changed | custom keyword 1 → 2 | UNKNOWN: unsupported semantics |
| schema_invalid | object → null, array, boolean or primitive | UNKNOWN: input schemas must be objects |

At schema locations only, type/required arrays are sets and outer enum member order is ignored. Each enum member and const value is an opaque JSON instance: object key order is ignored, but every literal array retains order, including arrays under instance keys named type/required/enum. Schema traversal never resolves instance-valued $ref keys. Unknown keyword values are opaque as well. Canonical JSON recursively sorts object keys in UTF-16 code-unit order, preserves array order and uses JSON primitive encoding. Hashing is SHA-256 over that encoding. Normalization copies only snapshot contract fields, fills optional tool fields with null, sorts tools and retains the first duplicate with a sorted duplicateNames statistic.

Snapshot validation returns `{ok, errors:[{path,message}]}`. It checks format/version, timestamp, metadata types, mandatory tool fields, duplicates, count consistency, finite JSON values, dense arrays, plain objects, cycles, depth (root depth zero), strings and object keys. Defaults are depth 64, 10,000 tools and 100,000 UTF-16 code units per string. It rejects overlong saved strings; collection truncation belongs to the collector. Byte/message/page limits belong to collection and file loading.

Rename hints never rename anything. For each removed tool the best added tool scoring at least .75 is retained, up to 50 hints in removed-name order. Score is `.6 * (1 - Levenshtein/maxNameLength) + .4 * canonicalInputEquality`. Ties use added-name code-unit order; added tools may appear in multiple hints. Different schemas cannot reach the threshold. Set-order normalization for compatibility does not alter the contract's canonical equality used in rename scoring.

Summary status counters count tools; severity counters count findings. Risk precedence is high (any BREAKING), unknown (any UNKNOWN), low (any NON_BREAKING), none. Unchanged entries require `all:true`; rename hints are disabled by `renameHints:false`.

Supported combinations: enum and const intersect by canonical instance identity. When both schemas have finite domains and only type, numeric intervals, length/item-count bounds, uniqueItems and documentation, these constraints, including uniqueItems, filter the finite sets before classification, suppressing redundant type/bound findings. Otherwise no complete finite-domain evaluation is claimed. Exact filtered sets are compared only when both sides are exactly evaluable; a filtered set is never compared with an unevaluated enum upper bound as if both were exact. With unsupported residual constraints, a raw removed value is BREAKING only if its prior admissibility is established; raw widening is NON_BREAKING only when the remaining predicates are identical. Other finite interactions are UNKNOWN. Existing UNKNOWN findings are retained; an unrelated widening or metadata change cannot downgrade aggregate risk. Combined inclusive/exclusive numeric endpoints use their strongest intersection; integer-only domains round endpoints only when both the rounded endpoint and its successor/predecessor (when needed) satisfy Number.isSafeInteger. An unsafe normalization returns UNKNOWN for the numeric change, in either direction, and cannot be hidden by accompanying NON_BREAKING documentation. For example, integer minimum:9007199254740992 ? exclusiveMinimum:9007199254740992 is UNKNOWN, never unchanged or NON_BREAKING. Large finite JSON numbers remain valid; exact finite-domain comparisons use relational comparisons without rounded integer arithmetic. Two provably empty numeric intervals compare equal. Constraints irrelevant to both declared type domains are ignored. A type narrowing with additional unanalysed constraints, or numeric tightening interacting with other constraints, is UNKNOWN rather than a claimed rejection witness. For example, type:string plus minimum:1 is unchanged; enum:[1] plus type:number is unchanged; integer minimum:1 and exclusiveMinimum:0 are identical.

Known limits: no remote references, general schema satisfiability solver, dialect negotiation, regex comparison, output compatibility analysis, or server execution. Boolean/tuple items are conservative UNKNOWN when changed. Legacy boolean exclusive bounds are UNKNOWN. Unsupported constraint interactions remain UNKNOWN where identified; the engine is not a theorem prover. NON_BREAKING findings do not cancel other findings. Cyclic references intentionally produce UNKNOWN even when text is identical. Validation is not a complete JSON Schema meta-validator. Levenshtein is quadratic in name lengths and hint candidate enumeration is removed × added; the 10,000-tool performance guarantee tested here concerns matched tool inventories.


## Snapshot and result evolution policy

Snapshot schemaVersion and result schemaVersion are independent of the package version. Version 1 is the only supported snapshot version. validateSnapshot rejects missing, malformed, older or future schemaVersion values at /schemaVersion, explicitly stating that only 1 is supported and there is no automatic migration. Consumers must not guess a compatible version or silently rewrite a version tag. A future incompatible structure or interpretation requires a new schemaVersion and an explicit migration outside this engine.

compareSnapshots validates before and then after, including duplicate-name and resource-limit checks, before normalization or comparison. An invalid input throws SnapshotValidationError (a TypeError subclass exported by src/diff/compare.js), with name='SnapshotValidationError', code='INVALID_SNAPSHOT', side='before'|'after', and errors=[{path,message}]. Its message identifies the side and fields. No result is emitted on invalid input. Library consumers using the package entry can catch by name/code and inspect errors; no new package-root export is promised here.

In v1, unknown additive snapshot metadata fields are accepted but carry no compatibility semantics. Result server metadata is copied through a fixed name/version/protocolVersion projection, never wholesale. JSON Schema's unknown keywords are different: their changes are reported UNKNOWN. Existing required fields and their types remain mandatory. Tools are validated rather than silently deduplicated on compare; normalizeSnapshot's keep-first behavior is a separate explicit collection operation.

Every emitted result has format='joons-mcp-diff/result', schemaVersion=1 and the documented fixed envelope and counter/risk invariants. This module does not accept persisted results as comparison inputs and provides no standalone result validator or automatic result migration. Consumers of saved results must check format and schemaVersion, validate the envelope/counters they use, ignore additive fields, and treat unknown change kinds/severities conservatively. They must reject unknown result versions rather than interpreting them as v1. Additive diagnostic change kinds may be introduced within v1; incompatible field types or meaning require a new result schemaVersion.

## JavaScript API JSON boundary and RS2 regression coverage

validateSnapshot accepts only dense arrays and plain data objects (Object.prototype or null prototype). Every array index must be an own data element: a hole is rejected at its index path, while an explicit null is a valid literal value. Class instances, Date/Map/Set/RegExp, boxed primitives, typed arrays, array subclasses, custom prototypes, proxies, accessors, symbol keys, hidden properties and extra non-index array properties are rejected anywhere, including metadata and literal enum/const values. Accessors are not invoked. Invalid structure returns before any typed field reads, so compareSnapshots rejects it with SnapshotValidationError before normalization can skip slots or call a non-JSON object's behavior. Schema meta-invalid but structurally JSON-valued nested input stays conservative rather than causing a generic comparison exception.

Structural traversal is bounded by maxDepth and additionally maxArrayLength=1,000,000 and maxNodes=1,000,000 by default. Oversized sparse arrays fail on length without scanning billions of slots; other sparse arrays fail at the first missing own index. The existing 10,000-tool and string-length limits still apply. The standalone canonicalization helpers expect validated JSON data; compareSnapshots enforces that boundary for both operands.

All 59 RS2 cases are preserved in test/fixtures/snapshots/rs2-regressions.json alongside the earlier 128 RS1 cases. test/diff-review2.test.js runs the new table, with explicit reconstruction tags for the two sparse JavaScript arguments that JSON cannot represent. Expected verdicts come from the documented semantics: RS2N030?032 are UNKNOWN under the deliberate safe-arithmetic limit, RS2N044 is unchanged because its entire finite domain is already unique, and sparse inputs require typed rejection. Additional tests cover both signs and both directions at safe-integer boundaries, exact large finite domains, canonical duplicate element identity, non-plain objects, nested sparse literals, validation budgets, and 832 dense JSON keyword/location combinations that must not crash the validated comparison API.
